# How ToneCustoms Works

**Purpose-led FiveM development, with a clear path from concept to customer-ready resource.**

At ToneCustoms, the goal is not simply to add another feature to a server. We develop gameplay and operational systems with a specific roleplay purpose, a practical implementation, and a documented experience for server owners.

This page explains our general development approach. It is not a promise that every resource will have the same features, timeline, or compatibility.

## 1. Start with the experience

We identify what players or server operators should be able to do, why it matters, and how the interaction should fit into a roleplay environment. That includes looking beyond the initial menu or animation to the complete gameplay loop.

For example, an interactive job may need a meaningful start, clear actions, progression, completion, and rewards. A server-management tool may need reliable permissions, clear feedback, and an understandable configuration.

## 2. Define the resource

Before a project is presented as a finished product, its intended scope, dependencies, configurable settings, and limitations should be clear. FiveM resources may use Qbox, QBCore, ESX, ox_lib, ox_inventory, ox_target, or other integrations, depending on the specific project.

Compatibility is documented **per resource**, not promised universally.

## 3. Build with consistency

ToneCustoms uses recognizable branding and project organization while allowing each resource to have its own interaction design. We aim for interfaces and gameplay that suit the system rather than reusing the same experience for every activity.

Private source code and protected assets are managed separately from public product information.

## 4. Review the full gameplay flow

Review covers more than whether a menu opens. Relevant checks may include:

- Player interaction and feedback
- Configuration and dependency requirements
- Server-side validation and persistent state where needed
- Inventory and item behavior where applicable
- Error handling and edge cases
- Installation and customer-facing instructions

A project may move through multiple rounds of development and correction. A working internal build is not automatically a published release.

## 5. Prepare clear product information

When a resource is approved for customers, its product information should explain what it does, how to install it, relevant compatibility details, and where to get help.

We separate **development showcases** from **store-listed products** so that a video or concept page is not mistaken for a currently purchasable resource.

## 6. Support and maintain

Customers can use our official support channels for product questions, installation help, and troubleshooting. Approved updates are communicated when released; there is no fixed update schedule.

Customer feedback can inform improvements, but requests do not automatically become promised features.

## Our working principles

| Principle | What it means |
| --- | --- |
| **Purpose** | Every system should serve a clear gameplay or operational need |
| **Immersion** | Player interactions should feel connected to the roleplay experience |
| **Configurability** | Relevant settings should be understandable and documented |
| **Quality** | Review the complete resource, not only its presentation |
| **Clarity** | Explain features, requirements, status, and limitations accurately |
| **Ownership** | Protect private development work and release only approved products |
